# 2026-09-15

## 调研：构建与发布流程（回答用户提问）

### 结论：本项目有**三条互不相关的发布轨道**，不要混为一谈

| 轨道 | 入口 | 触发 | 产物 |
|---|---|---|---|
| npm 包发布（dsh 家族） | `release:*` 脚本 | 手动 `workflow_dispatch`，需 `dsh-v*` tag | `dist/npm/*.tgz` |
| 生产部署（jdcloud 线上服务） | `compose.yaml` | 本地 `docker compose up` | Docker 镜像 + Caddy 反代 |
| 其他 | docs/desktop/python/native | 各自 workflow | 见下 |

### 轨道 A：npm 发布（已核验脚本源码）
本地 bump → 提交 → 人工打 tag → 手动 dispatch CI：
```sh
pnpm run release:dsh patch          # 或 minor|major|x.y.z，写入全家族+根版本
git commit && git tag dsh-v<version> && git push --tags
# 然后 GitHub Actions 手动跑 release-publish.yml
```
- 版本**必须本地写入仓库**，CI 只校验不写（`release:verify` 校验：家族版本一致、
  `private:true` 已移除、tag 属于该家族且版本匹配）。
- 发布判定是**按包查 registry**：不存在→发；存在且 sha512 相同→跳过；存在但内容不同→**失败**
  （说明改了内容没升版本）。这让重跑安全（幂等）。
- dsh 家族 dist-tag：`alpha`/`canary` → 同名 tag，其他预发布（含 `rc`）→ `next`，稳定版 → `latest`。
- `pack` 与 `publish` 分离：pack 无凭据（PR 也跑），publish 需 `npm-publish` environment 审批。

### 轨道 B：生产部署 —— **发现缺陷：Dockerfile 缺失**
`compose.yaml`（由 `22e3f99a8c` 引入）声明：
```yaml
build:
  context: .
  dockerfile: Dockerfile     # ← 此文件全仓不存在
```
- 已用 `git log --all --diff-filter=A -- Dockerfile*` 确认：**历史上从未存在过**。
- 无 `.dockerignore`，无 `.env.example`（`.env` 未跟踪且只含 `JDCLOUD_DEFAULT_BASE_URL`，
  而 compose 需要 `JDCLOUD_HARNESS_TRUSTED_HOST` 与 `GPT_API_KEY`，故 `docker compose up` 会直接失败）。
- **结论：Docker 部署路径目前不可用，需先补 Dockerfile。** 这是回答用户问题时必须点明的。

### 关键架构约束（写 Dockerfile 时绕不开）
- `dsh web` **显式拒绝** `--host 0.0.0.0`（`packages/bundle/web-app/src/startup.ts:74`，
  理由是「会把远程代码执行暴露到网络」）→ 因此 compose 用 **Caddy 同 network namespace 反代到
  `127.0.0.1:3080`**，harness 自身只监听 loopback。
- 默认 `host: 127.0.0.1`、`port: 3080`（`packages/bundle/web-app/cordis.patch.yml:139-140`）。
- 认证不是 API token，而是**浏览器会话**：进程级 launch token（`randomBytes(32)`）经根 URL
  `?token=` 换 HMAC Cookie `dsh-auth-<sha256(authority)>`；`/api` 由 host/origin 信任栅栏校验
  （`isTrustedApiRequest` + `trustedHosts`）。所以公网部署**必须**传 `--trusted-host`。
- compose 设 `NODE_ENV: production`、`DSH_HOME=/var/lib/jdcloud-harness`（持久化 settings/profiles/
  sessions/attachments），并挂 `/workspace` 存放会话产物。

### 轨道 C：构建命令与产物目录（已实测存在）
| 命令 | 产物 |
|---|---|
| `pnpm run build:native-system` | `native/system/packages/*/bin/**`（C addon，需 `cc`；非 linux/darwin 静默跳过） |
| `pnpm run build:lib:host` | 各包 `lib/`（tsdown，host 面） |
| `pnpm run build:lib:client` | 各包 `lib/client.js`（tsdown，client 面） |
| `pnpm run build:web` | `apps/web/dist`（vite；当前 119 个文件） |
| `pnpm run build` | 上述三步 + `.dsh-build/client-build-environment.json` |
| `pnpm run build:desktop` | `apps/desktop/lib`（**不在 `build` 里**，需单独跑） |

- `pnpm run build` 顺序固定：删 build record → native → lib → web → 写 build record。
- profile 只有 `official` 一个；`build:official` **要求环境已设** `DSH_CLIENT_COMMIT_HASH`
  与 `DSH_CLIENT_VERSION`，否则抛错。
- 根 `dist/` **不存在**，只由发布脚本按需创建（`--out dist/npm`）。

### 环境要求（已核验）
- Node `^22.19.0 || >=24.0.0`（本机 v22.22.2 ✓）；pnpm `11.7.0`（本机 ✓）。
- 无 `.nvmrc`/`.node-version`；**无 Rust**（native 是 C + `cc`/`musl-gcc`，不用 node-gyp）。
