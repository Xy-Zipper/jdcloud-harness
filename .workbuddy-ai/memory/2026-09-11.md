## 定位 jdcloud_lowcode_upload_image 上传失败根因

输入：`D:\Downloads\dsh-session-session-c5b0cbe6-...zip`（会话导出包，含 session.v3.jsonl + media）
输出：`D:\Downloads\dsh-session-c5b0cbe6\上传报错分析报告.md`

**结论**：报错 `JDCLOUD_LOWCODE_ATTACHMENT_REQUIRED` 与 `/api/file/uploader` 无关，该接口从未被调用。

- 断点：`packages/jdcloud/tool-jdcloud-lowcode/src/tools.ts:505-531` 的 `requireSessionImage()` 前置守卫。
- 根因：`findImage()` 用 `String(block.attachment.attachmentId) === attachmentId` 严格等值比较。
  会话内存储值为 `sha256:<64hex>`，模型传入的是裸 64hex（丢了 `sha256:` 前缀），3 次调用参数逐字节相同。
- 模型侧来源：`packages/llm/llm/src/content.ts:48-52` `imageIdentity()` 生成 `"name" (sha256:…)` 句柄，
  经 `llm-deepseek/src/serialize.ts:128-139` 注入提示词；工具描述 `tools.ts:219-223` 未点明前缀属于 id 的一部分。
- 放大因素：错误文案原样回显模型传错的值，不提示正确格式，导致模型无法自我纠正。
- 附带发现：`jdcloud_lowcode_create`（workflow 类菜单）透传后端 `result` 作为 id
  （`tools.ts:286`），该值与真实记录 `_id` 末位不一致（…21c vs …21b），导致随后 `jdcloud_lowcode_get` 报「数据不存在」。

**建议修复**（尚未落地）：`requireSessionImage` 增加 `sha256:` 前缀归一化 + 改写工具描述与报错文案；
`tests/lowcode.spec.ts` 补一条裸 hex 入参回归用例。

## 排查手法（可复用）

会话导出包为 JSONL，事件类型：`user/message`、`assistant/message`、`tool/call`、`tool/result`、
`agent/inbox/spliced`（含原始附件 `attachment.attachmentId`）、`request/header`（含模型侧完整工具 schema）。
用 Python 按事件类型抽取成可读 transcript，是定位「模型看到了什么 vs 传了什么」最快的方式。
