# 2026-10-21

## 修复 docker build 失败：tsdown `[@deepseek-ai/dsh-root] Cannot find entry`

**根因**：工作区里残留 4 个无 `package.json` 的空壳目录（改名后的旧包），仅含 `lib/` 与 `node_modules/`：

- `packages/api/ontology-auth-controller`
- `packages/bundle/ontology-login`
- `packages/client/ui-ontology-login`
- `packages/ontology/tool-ontology`

它们匹配 tsdown 的 `packages/*/*` workspace glob。本地因残留的 `lib/types/index.js` 恰好满足入口 glob 而被掩盖；`.dockerignore` 忽略 `**/lib`、`**/node_modules` 后这些目录在镜像里变成空目录，tsdown 读不到 manifest 就回落到根配置，入口 `lib/types/{index,invariant,startup}.js` 解析失败，错误被标成根包名 `@deepseek-ai/dsh-root`。

**处理**：
1. `tsdown.config.ts` 的 `workspaceExcludes` 增加这 4 个目录（沿用既有 `!packages/...` 负向 glob 约定），并补注释说明空目录会继承根配置。
2. 本地残留目录移到 `.tmp/residue-backup-20261021/`（可还原），工作区恢复干净。

**验证**：把某个残留目录的 `lib` 移走即可本地复现原始报错；加排除后 `tsdown --env.DSH_BUILD_FACE host` 退出码 0、无 entry 错误、无 `dsh-root` 幽灵单元。

**坑点**：`tsdown.config.ts` 由 Node 原生类型剥离直接加载，块注释里不能出现 `*/` 序列（例如写 `packages/*/*` 会提前闭合注释并触发 `ERR_INVALID_TYPESCRIPT_SYNTAX`）。

**备选清理**：`pnpm run clean`（scripts/clean.ts）本身就会删除「只含已知残留」的无 manifest 包目录。

**端到端验证**：`docker build --build-arg DSH_CLIENT_COMMIT_HASH=<HEAD> --tag jdcloud-harness:local .` 成功（8m54s，镜像 3.32GB，日志 `build: recorded 267 client artifact(s)`，无 `Cannot find entry`）。注意：并发跑两个 docker build 会导致 `frontend grpc server closed unexpectedly`，构建需单条串行执行。

## 修复线上「读取失败：typert gateway: workspaceFiles/changes: no active Remote method exports this endpoint」

**现象**：部署实例里点击文件预览报该错。

**根因**：`packages/api/workspace-files/src/index.ts` 第 31 行有**运行时**导入 `import { WorkspaceId } from '@deepseek-ai/dsh-workspace'`，但该包 `package.json` 从未声明这个依赖，pnpm 因此不在包内建链接。构建产物 `lib/index.js` 保留裸导入 → 镜像里 `import('@deepseek-ai/dsh-api-workspace-files')` 抛 `ERR_MODULE_NOT_FOUND: Cannot find package '@deepseek-ai/dsh-workspace'` → 插件 import 失败 → `workspaceFiles` 服务不注册 → 网关 `resolveSrcDescriptor` 找不到端点，报 `gateway/invocation-unavailable`。

本地开发看不出来：源码态由 tsx 按 tsconfig paths 解析，测试同理；只有跑构建产物才暴露。

**诊断方法**（可复用）：`docker run` 起探针容器后看启动日志，会出现
`dsh: warning: 3 entries did not activate` / `workspace-files (...): failed to import` / `ui-deliverables`、`external-api` 因 `waiting for service: workspaceFiles` 而 pending。

**修复**：`packages/api/workspace-files/package.json` 的 `peerDependencies` 与 `devDependencies` 补 `@deepseek-ai/dsh-workspace: workspace:*`（与 `packages/api/workspace-controller` 的既有写法一致）；`pnpm install --lockfile-only` 更新 `pnpm-lock.yaml`（diff 仅 3 行，在 `packages/api/workspace-files` 的 devDependencies 下）。

**验证**：本地 `import('./lib/index.js')` 由 FAIL 变 OK；容器内补链接后重启，启动日志的 `did not activate` 警告消失。镜像重建因 npm registry 超时（`TimeoutError`）失败，lockfile 本身已通过 `--frozen-lockfile` 的 supply-chain 校验。

**注意**：本机 `pnpm install --frozen-lockfile` 耗时约 35 分钟，docker build 内 `pnpm install` 每次全量下载约 1360 个包，网络差时极易超时；可考虑给 Dockerfile 的 install 步骤加 BuildKit 缓存挂载。
